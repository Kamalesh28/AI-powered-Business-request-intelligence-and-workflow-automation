# Architecture

## Design principles

The system is layered so deterministic business policy and auditable data operations are independent of Streamlit. Dependencies point inward: the UI calls application services; services call rules, repositories, and optional adapters; rules and domain validation do not import UI or database code.

## Component view

```text
Streamlit interface
    │  validated commands / display models
    ▼
Application services
    ├── Intake service ───────────────► Input/domain validation
    ├── Processing service ───────────► Classification orchestrator
    ├── Review service ───────────────► Review/state policy
    └── Reporting service ────────────► Pandas report calculations
                                           │
                  ┌────────────────────────┴───────────────────────┐
                  ▼                                                ▼
        Rule-based classifier                            Optional Ollama adapter
        (baseline; deterministic)                        (local; schema-validated)
                  │                                                │
                  └─────────────────► Validated decision ◄────────┘
                                                │
                                                ▼
                                      SQLite repository layer
                                      requests / runs / reviews
                                                │
                                                ▼
                                           SQLite database
```

## Proposed package boundaries

```text
business_request_intelligence/
  app.py                         # thin Streamlit composition root
  domain/
    models.py                    # dataclasses/enums/value objects
    validation.py                # intake and decision schemas
    states.py                    # allowed lifecycle transitions
  rules/
    taxonomy.py                  # controlled vocabulary and threshold configuration
    baseline.py                  # deterministic rules, precedence, evidence
  services/
    intake.py                    # validated request creation
    processing.py                # mode selection, persistence orchestration
    review.py                    # human confirmation/correction flow
    reporting.py                 # testable Pandas aggregations/KPI definitions
  storage/
    database.py                  # SQLite connection, migration/bootstrap
    repositories.py              # parameterized persistence/query operations
  integrations/
    ollama.py                    # optional localhost adapter only
  ui/
    intake_page.py
    review_page.py
    dashboard_page.py
  seed/
    synthetic_data.py
  tests/
    ...
```

The exact directory/package name can be finalized at implementation, but separation of concerns is mandatory.

## Data model

### `requests`

| Field | Notes |
| --- | --- |
| `request_id` | Primary key, generated by application. |
| `title`, `description` | Validated synthetic business-request text. |
| `department`, `channel`, `declared_urgency` | Controlled values. |
| `submitted_at_utc` | ISO-8601 UTC timestamp. |
| `status` | `submitted`, `classified`, `needs_review`, or `reviewed`. |
| `is_synthetic` | Always true for this project. |

### `processing_runs`

| Field | Notes |
| --- | --- |
| `processing_run_id`, `request_id` | Primary and foreign keys. |
| `processing_mode` | `rule_based` initially; `ollama_local` only after Stage 2. |
| `processed_at_utc`, `engine_version` | Reproducibility/audit fields. |
| `proposed_category`, `proposed_priority`, `confidence` | Must pass controlled-vocabulary/range validation. |
| `evidence_json` | Rule hits or safe structured rationale. |
| `raw_output_json` | Optional safe audit payload; never trusted directly. |
| `validation_status`, `error_message` | Valid/invalid/failure trace without exposing secrets. |

### `reviews`

| Field | Notes |
| --- | --- |
| `review_id`, `request_id`, `processing_run_id` | Links a human decision to its proposal. |
| `reviewer_name`, `reviewed_at_utc` | Accountability and time. |
| `final_category`, `final_priority` | Controlled, validated values. |
| `category_corrected`, `priority_corrected` | Explicit correction flags. |
| `rationale` | Optional bounded text. |

## Decision and validation flow

1. Validate and normalize an intake command, then persist the request.
2. Execute rule-based classification in Stage 1 and build a typed proposed decision.
3. Validate all decision fields, confidence range, evidence shape, and allowed labels before persistence.
4. Append a processing run, update request status according to state policy, and expose decision evidence.
5. If review is required, validate a reviewer command, append a review record, and transition the request to `reviewed`.
6. Reporting queries persisted records through repositories; Pandas computes metrics; Plotly only renders returned datasets.

## Error boundaries

- UI converts user mistakes into field feedback and expected operational faults into concise alerts.
- Services own transaction scope and may translate low-level storage/adapter exceptions to application errors.
- Repository code alone issues SQL and always uses bound parameters.
- Optional Ollama adapter handles connection/timeout/response parsing but may return only a validated decision or an explicit failure result.

## Testing strategy

- Unit tests: input constraints, rule precedence, confidence and review routing, enum/schema validation, KPI formulas.
- Repository integration tests: temporary SQLite database, migrations, foreign keys, append-only processing/review records, query filters.
- Service tests: valid/invalid transitions and error behavior, using fake repositories/adapters where useful.
- UI smoke tests only after the service layer is stable; business logic must remain testable without Streamlit.
- Ollama contract tests use static fixtures/mocks. A manually run local integration check may be documented separately and must not be presented as automated proof unless it is automated.
